# Parties + Catalog Domain/Persistence Foundation

## Status

Implementation slice in review. This is the first business-state extension over the accepted transactional v1 persistence substrate.

## Scope delivered

### Domain
- `Party` aggregate with PERSON/ORGANIZATION kind;
- CUSTOMER/SUPPLIER commercial roles;
- separate residence country, tax-residence country and typed fiscal identities;
- no authoritative `IsForeign` flag;
- versioned mutation methods for future optimistic concurrency;
- fiscal identity duplicate/validity invariants;
- `CommercialItem` aggregate with PRODUCT/SERVICE kind;
- product/service catalog works for service-only and mixed businesses;
- SERVICE + `trackInventory=true` is rejected by Domain;
- item deactivation is non-destructive and versioned;
- `ItemCategory` foundation.

### Application
- `IPartyRepository` and `ICommercialItemRepository` inward ports;
- `CreatePartyUseCase` implementing `API-PTY-002` application behavior;
- `CreateCommercialItemUseCase` implementing `API-CAT-002` application behavior;
- explicit permission + organization-scope checks inside Application, not only controllers;
- mandatory idempotency reservation/replay handling;
- durable `party.created` / `catalog.item.created` audit evidence;
- Outbox integration events;
- business state, idempotency, audit and Outbox participate in the same transaction.

### Infrastructure
Provider-neutral EF Core records/repositories and tables:

- `v1_parties`;
- `v1_party_roles`;
- `v1_party_fiscal_identities`;
- `v1_commercial_items`;
- `v1_item_categories`.

Repositories stage data only. They contain no transaction begin/commit/rollback and no independent `SaveChanges`.

### Migration stream
The v1 persistence schema is now materialized through EF Core migrations rather than production `EnsureCreated`.

`20260829023000_V1InitialPersistence` creates the accepted cross-cutting tables plus the first Parties/Catalog business tables using provider-portable migration operations.

`20260829023100_V1CatalogCategoryForeignKey` enforces the Catalog category reference.

The same migration stream is executed against PostgreSQL and MySQL in CI. Provider-specific SQL is generated by the selected EF Core provider; runtime business writes remain free of raw mutation SQL.

## Atomicity proof obligation

The integration suite deliberately performs this sequence against both relational engines:

```text
BEGIN
  reserve idempotency
  SaveChanges
  stage Party business rows
  stage durable audit
  stage Outbox
  SaveChanges
  inject exception
ROLLBACK
```

A fresh context must then observe zero Party, role, fiscal identity, audit, Outbox and idempotency rows.

The success path executes the actual Application use cases and proves Party/CommercialItem rows, durable audit, completed idempotency and Outbox commit together. Replaying the Party command with the same idempotency identity must return the canonical original Party without duplicating business/audit/outbox rows.

## Deliberate boundaries

This slice does **not** claim the complete Parties/Catalog API surface is implemented.

Implemented application operations in this slice:
- `createParty` (`API-PTY-002`);
- `createItem` (`API-CAT-002`).

Still pending in the same vertical family:
- list/get/update Party;
- add/update fiscal identity;
- set Party roles;
- Party account summary (depends on Receivables/Payables projections);
- list/get/update/deactivate item;
- item category commands/queries;
- tax-profile query (Taxation-owned);
- WebApi v1 controllers/contracts for the operations above.

No Sales/POS/Fiscal implementation begins until this foundation is accepted and its migration + transaction tests are green.

## Clean Architecture invariant

Domain contains no EF/provider/ASP.NET dependencies. Application depends only on Domain and inward cross-cutting contracts. Infrastructure maps/persists Domain state. Future controllers remain delivery adapters and cannot reach `V1PersistenceDbContext` or repositories directly.
