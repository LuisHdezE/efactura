# W1.5 Terminal field contract proposal

Status: `PROPOSED / OWNER_DECISION_REQUIRED / IMPLEMENTATION_NOT_AUTHORIZED`

Proposal baseline: `main@04fd00362f7535e15be8b9de8f10649eeac84192`.

Scope:

- `API-ORG-007 listTerminals`
- `API-ORG-008 registerTerminal`
- `API-ORG-009 getTerminal`
- `API-ORG-010 updateTerminal`

This document is a bounded contract candidate created to close the field-level prerequisite recorded in `W1_5_TERMINALS_READINESS.md`. It is deliberately not implementation authority until Luis explicitly accepts the contract and the governed change is merged.

No Domain, Application, Infrastructure, WebApi, migration, deployment or production database change is authorized by this proposal.

## 1. Already-governed constraints

The following points are evidence from the accepted API program and current architecture, not new choices introduced by this proposal:

- `listTerminals` is GET `/api/v1/terminals` with `organization.read`.
- `registerTerminal` is POST `/api/v1/terminals` with `organization.manage` and requires `Idempotency-Key`.
- `getTerminal` is GET `/api/v1/terminals/{terminalId}` with `organization.read`.
- `updateTerminal` is PATCH `/api/v1/terminals/{terminalId}` with `organization.manage` and requires `Idempotency-Key`.
- terminal is organization/POS operational master data and is distinct from offline/sync device registration.
- successful registration/update requires durable `organization.terminal.registered|updated` evidence.
- mutable resources use the existing application-managed optimistic-concurrency convention and stale writes map to `409 concurrency_conflict / stale_version`.
- the current organization slice already establishes server-owned organization context, provider-neutral persistence, versioned master data, idempotency, durable audit and transactional outbox patterns.

## 2. Governing design principle

The proposed public Terminal resource is intentionally small.

It answers only five operational questions:

1. Which terminal is this?
2. What stable operator-facing code identifies it?
3. What display name should humans see?
4. Which organization location owns it operationally?
5. Is it active and at what optimistic-concurrency version?

W1.5 does not become a hardware inventory, device enrollment system, fiscal-series configuration surface or arbitrary metadata bag.

## 3. Proposed canonical resource

The proposed public read projection is:

```text
TerminalDto
- id: string
- organizationId: string
- code: string
- name: string
- locationId: string
- active: boolean
- version: long
```

### `id`

- generated by the server;
- immutable;
- opaque to clients;
- never accepted from the create/update body;
- consumers must not depend on a particular UUID/GUID textual representation even if the implementation follows the current organization-ID generation pattern.

### `organizationId`

- derived from the authoritative request organization context;
- returned in the projection for consistency with current organization DTOs;
- never body-overridable.

### `code`

`code` is a deliberate new contract choice. The existing repository did not previously define a terminal business code.

Proposal:

- required on registration;
- trimmed and normalized to uppercase invariant before persistence/comparison;
- maximum 64 characters;
- accepted characters: `A-Z`, `0-9`, `.`, `_`, `-`;
- unique within one organization;
- immutable after registration.

The code is the stable human/operator-facing identifier. Changing a display name or moving a terminal to another location does not change its business identity.

### `name`

- required;
- trimmed;
- maximum 120 characters, aligning with the current `FiscalLocation.Name` boundary;
- mutable.

### `locationId`

- required;
- references an existing `FiscalLocation` in the resolved organization;
- mutable through `updateTerminal` under the rules in section 7;
- does not imply any device-registration association.

### `active`

W1.5 proposes a two-state operational model instead of inventing a larger lifecycle enum:

- `true` = active;
- `false` = inactive.

Registration creates an active terminal. Deactivation is represented by `active=false`; there is no public delete operation in W1.5.

### `version`

- positive application-managed integer;
- starts at `1`;
- increments after every successful update mutation;
- `expectedVersion` is required for PATCH.

## 4. Proposed request contracts

### API-ORG-008 `registerTerminal`

```text
TerminalCreateRequest
- code: string
- name: string
- locationId: string
```

Server-owned outcomes:

- `id` is generated by the server;
- `organizationId` is resolved from request context;
- `active=true`;
- `version=1`.

The same idempotency key + same canonical payload replays the original successful resource and sets `Idempotent-Replayed: true`. Same key + changed payload uses the existing `409 idempotency_key_reused / payload_mismatch` behavior.

### API-ORG-010 `updateTerminal`

```text
TerminalUpdateRequest
- name: string
- locationId: string
- active: boolean
- expectedVersion: long
```

Although the method is PATCH, this proposal follows the existing organization-update convention: the body is the complete mutable snapshot rather than a JSON Merge Patch document. `code`, `id` and `organizationId` are not mutable fields.

## 5. Proposed read behavior

### API-ORG-007 `listTerminals`

Proposed optional query filters:

- `active`: nullable boolean, default `true`;
- `locationId`: optional location filter.

Behavior:

- omitted `active` returns active terminals only, matching the current `LocationsController` default behavior;
- `active=null` at the application boundary means both active and inactive rows when explicitly represented by the WebApi binding strategy;
- omitted `locationId` lists terminals across the resolved organization;
- supplied `locationId` limits the result to that organization location;
- projection order is deterministic by normalized `code`, then `id`.

No pagination is proposed for W1.5. This keeps the organization-master behavior aligned with the current bounded location list. Pagination can be introduced later through a separately governed backward-compatible contract if scale proves it necessary.

### API-ORG-009 `getTerminal`

Returns the exact canonical `TerminalDto` for the route ID inside the resolved organization or the not-found behavior in section 8.

## 6. Authorization and organization boundary

W1.5 metadata administration follows the current Organization slice rather than inventing a second authorization subsystem:

- every request requires the endpoint's accepted `organization.read` or `organization.manage` permission;
- organization is resolved through the existing V1 organization context behavior;
- requested organization must exist in the actor's company scope;
- body fields cannot switch organization;
- cross-organization terminal/location identifiers must not disclose the existence of resources outside the resolved organization.

This proposal does not redefine operational `LocationScopes` or `TerminalScopes`. Existing operational/fiscal flows continue enforcing those scopes where already governed. A future change that makes organization-master metadata itself terminal-scope-filtered requires an explicit contract change rather than an accidental side effect of W1.5.

## 7. Location and activation rules

The terminal-to-location relationship is mandatory.

### Registration

A new terminal may be registered only against an existing active fiscal location in the same organization.

### Reassignment

Reassignment is allowed through `updateTerminal` and requires:

- current `expectedVersion`;
- destination location exists inside the same organization;
- destination location is active.

The terminal ID and code remain unchanged after reassignment.

### Reactivation

Changing `active=false` to `active=true` is allowed only if the terminal's requested location is active.

### Cleanup after a location becomes inactive

An already-inactive terminal may remain readable when its historical/current location later becomes inactive. W1.5 must still allow an administrator to keep it inactive and update its display name without forcing a move merely to perform cleanup.

An active terminal cannot be newly assigned or reactivated onto an inactive location.

## 8. Proposed stable problem semantics

| Situation | HTTP | code | conflictType |
|---|---:|---|---|
| terminal not found in resolved organization | 404 | `organization.terminal_not_found` | n/a |
| location missing/cross-organization | 404 | existing `organization.location_not_found` | n/a |
| target location inactive when an active binding is required | 409 | `organization.terminal.location_inactive` | `inactive_location` |
| duplicate normalized terminal code in organization | 409 | `organization.terminal.code_duplicate` | `duplicate_terminal_code` |
| stale `expectedVersion` | 409 | existing `concurrency_conflict` | `stale_version` |
| same idempotency key with changed payload | 409 | existing `idempotency_key_reused` | `payload_mismatch` |

Field validation remains HTTP 400 through the existing Problem Details pipeline. Proposed domain validation codes include:

- `organization.terminal.code_required`
- `organization.terminal.code_invalid`
- `organization.terminal.name_required`
- `organization.terminal.location_required`
- `organization.terminal.version_invalid`

## 9. Uniqueness boundary

The proposed terminal business-key invariant is:

```text
UNIQUE (OrganizationId, NormalizedCode)
```

It is intentionally not unique by `locationId`, `name`, hardware identifier, IP address, MAC address or device registration.

Moving a terminal between locations therefore preserves the same terminal identity and code.

The implementation must make normalization deterministic across PostgreSQL and MySQL rather than relying on provider-specific collation behavior.

## 10. Mutation evidence and idempotency boundary

Proposed internal idempotency scopes:

```text
organization.terminal.register:{organizationId}
organization.terminal.update:{organizationId}:{terminalId}
```

A successful registration/update must commit the following atomically with the terminal mutation:

- completed idempotency record;
- durable audit event;
- transactional outbox event.

Material evidence may include:

- terminal ID;
- normalized code;
- location ID;
- active state;
- resulting version.

It must not include device secrets, bearer tokens, offline grants, MAC addresses, IP addresses, certificate material or other credentials because those are outside the W1.5 Terminal contract.

## 11. Explicitly excluded from W1.5

The following fields/capabilities are not part of this proposal:

- device ID or sync-device binding;
- client operation ID;
- device secret, API key, refresh token or bearer token;
- MAC/IP address;
- hardware fingerprint, serial number or machine UUID;
- printer model/configuration;
- cash drawer configuration;
- fiscal-series/CAE allocation configuration;
- arbitrary JSON metadata;
- last-seen/heartbeat telemetry;
- online/offline state;
- hard delete endpoint;
- automatic terminal creation from sales, CAE or sync activity.

These exclusions prevent the operational terminal master from silently absorbing future Device, Sync, Fiscal or Technical Operations responsibilities.

## 12. Persistence implications if accepted

Acceptance of this public contract would authorize a refreshed implementation-readiness design, not an immediate production migration.

The expected additive master-data persistence would need to represent at least:

- terminal ID;
- organization ID;
- normalized code;
- display name;
- location ID;
- active flag;
- application version;
- normal persistence timestamps if required by the existing V1 record convention.

The exact table/index/FK names remain implementation details to derive after contract acceptance. Production schema promotion remains a separate explicit approval gate.
