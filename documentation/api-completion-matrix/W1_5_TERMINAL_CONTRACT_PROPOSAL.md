## 1. Endpoint scope

| API ID | operationId | Method / path | Permission | Idempotency |
|---|---|---|---|---|
| `API-ORG-007` | `listTerminals` | GET `/api/v1/terminals` | `organization.read` | NO |
| `API-ORG-008` | `registerTerminal` | POST `/api/v1/terminals` | `organization.manage` | REQUIRED |
| `API-ORG-009` | `getTerminal` | GET `/api/v1/terminals/{terminalId}` | `organization.read` | NO |
| `API-ORG-010` | `updateTerminal` | PATCH `/api/v1/terminals/{terminalId}` | `organization.manage` | REQUIRED |

No additional public endpoint is introduced by W1.5.

## 2. Canonical Terminal resource

```text
TerminalDto
- id: string
- organizationId: string
- code: string
- name: string
- locationId: string
- active: boolean
- version: long
```

### `id`

- generated by the server;
- immutable and opaque to clients;
- never accepted from create/update bodies.

### `organizationId`

- resolved from the authoritative V1 organization context;
- returned for consistency with current organization DTOs;
- never body-overridable.

### `code`

- required on registration;
- trimmed and normalized with invariant uppercase semantics before persistence/comparison;
- maximum 64 characters;
- allowed characters: `A-Z`, `0-9`, `.`, `_`, `-`;
- unique inside one organization;
- immutable after registration.

The accepted business-key invariant is:

```text
UNIQUE (OrganizationId, NormalizedCode)
```

Normalization must be deterministic across PostgreSQL and MySQL and must not depend on provider collation behavior.

### `name`

- required;
- trimmed;
- maximum 120 characters;
- mutable.

### `locationId`

- required;
- references an existing `FiscalLocation` in the resolved organization;
- mutable through `updateTerminal` under the rules below.

### `active`

The accepted W1.5 lifecycle is intentionally two-state:

- `true` = active;
- `false` = inactive.

Registration creates an active terminal. There is no public terminal DELETE operation in W1.5.

### `version`

- positive application-managed integer;
- starts at `1`;
- increments after every successful terminal update;
- `expectedVersion` is required for PATCH.

## 3. Request contracts

### API-ORG-008 `registerTerminal`

```text
TerminalCreateRequest
- code: string
- name: string
- locationId: string
```

Server-owned outcomes:

- generated `id`;
- resolved `organizationId`;
- `active=true`;
- `version=1`.

Same idempotency key + same canonical payload replays the original successful terminal and sets `Idempotent-Replayed: true`. Same key + changed payload uses the existing `409 idempotency_key_reused / payload_mismatch` behavior.

### API-ORG-010 `updateTerminal`

```text
TerminalUpdateRequest
- name: string
- locationId: string
- active: boolean
- expectedVersion: long
```

Although the method is PATCH, W1.5 follows the existing organization-update convention: the body is the complete mutable snapshot rather than a JSON Merge Patch document. `id`, `organizationId` and `code` are immutable.

## 4. Read behavior

### API-ORG-007 `listTerminals`

Accepted optional filters:

- `active`: nullable boolean, default `true`;
- `locationId`: optional location filter.

Behavior:

- omitted `active` returns active terminals only;
- application-level `active=null` means both active and inactive terminals;
- omitted `locationId` lists terminals across the resolved organization;
- supplied `locationId` limits the result to that location in the resolved organization;
- deterministic ordering is normalized `code`, then `id`;
- no pagination is introduced in W1.5.

### API-ORG-009 `getTerminal`

Returns the canonical `TerminalDto` for the route ID inside the resolved organization or the stable not-found behavior defined below.

## 5. Authorization and scope

- endpoint permissions remain exactly `organization.read` and `organization.manage`;
- organization is resolved through the existing V1 organization context;
- actor company scope must contain the resolved organization;
- request bodies cannot switch organization;
- cross-organization terminal/location references must not disclose resources outside the resolved organization.

W1.5 does not redefine existing operational `LocationScopes` or `TerminalScopes`. Existing sales/fiscal flows keep their governed scope checks.

## 6. Location and activation invariants

### Registration

A new terminal may be registered only against an existing active `FiscalLocation` in the same organization.

### Reassignment

Reassignment through `updateTerminal` is allowed when:

- `expectedVersion` is current;
- destination location exists in the same organization;
- destination location is active.

Terminal `id` and `code` remain unchanged.

### Reactivation

Changing `active=false` to `active=true` is allowed only when the requested location is active.

### Inactive terminal on inactive location

An already-inactive terminal may remain readable when its assigned location later becomes inactive. Administrators may keep it inactive and update its display name without requiring a move.

### Location deactivation dependency

The accepted invariant extends existing `API-ORG-006 updateLocation` behavior:

- changing a fiscal location from active to inactive is rejected while active terminals remain assigned;
- administrators must first deactivate or reassign those terminals;
- terminal records are never silently cascade-deactivated;
- terminal records are never hard-deleted because a location is deactivated.

## 7. Stable Problem Details semantics

| Situation | HTTP | code | conflictType |
|---|---:|---|---|
| terminal not found in resolved organization | 404 | `organization.terminal_not_found` | n/a |
| location missing/cross-organization | 404 | existing `organization.location_not_found` | n/a |
| target location inactive when an active binding is required | 409 | `organization.terminal.location_inactive` | `inactive_location` |
| deactivating a location while active terminals remain | 409 | `organization.location.active_terminals_exist` | `active_terminal_dependency` |
| duplicate normalized terminal code | 409 | `organization.terminal.code_duplicate` | `duplicate_terminal_code` |
| stale `expectedVersion` | 409 | existing `concurrency_conflict` | `stale_version` |
| same idempotency key with changed payload | 409 | existing `idempotency_key_reused` | `payload_mismatch` |

Validation remains HTTP 400 through the existing RFC 9457 Problem Details pipeline. Domain validation codes include:

- `organization.terminal.code_required`
- `organization.terminal.code_invalid`
- `organization.terminal.name_required`
- `organization.terminal.location_required`
- `organization.terminal.version_invalid`

## 8. Idempotency, audit and outbox

Accepted internal idempotency scopes:

```text
organization.terminal.register:{organizationId}
organization.terminal.update:{organizationId}:{terminalId}
```

Successful registration/update must atomically persist:

- the terminal mutation;
- completed idempotency evidence;
- durable audit evidence;
- transactional outbox evidence.

Accepted audit semantics remain `organization.terminal.registered` and `organization.terminal.updated`.

Material evidence may include terminal ID, normalized code, location ID, active state and resulting version. It must not contain secrets, bearer tokens, device credentials or sync grants.

## 9. Terminal vs Device boundary

W1.5 Terminal is organization/POS operational master data. It is not Device/Sync registration.

Explicitly excluded from W1.5:

- sync device ID/binding;
- client operation ID;
- API keys, refresh tokens, bearer tokens or device secrets;
- MAC/IP address;
- hardware fingerprint, serial number or machine UUID;
- printer/cash-drawer configuration;
- CAE/fiscal-series configuration;
- arbitrary JSON metadata;
- heartbeat/last-seen/online-offline telemetry;
- hard delete;
- implicit terminal creation from sales, fiscal or sync activity.

Any future Terminal-to-Device relationship requires a separate governed contract.

## 10. Persistence implications

The bounded W1.5 implementation may introduce additive provider-neutral persistence representing at least:

- terminal ID;
- organization ID;
- normalized code;
- name;
- location ID;
- active flag;
- application version;
- normal persistence timestamps where required by V1 record conventions.

The repository must support an efficient active-terminal dependency query for location deactivation.

Exact table/index/FK names are implementation details derived from this accepted contract. Production schema promotion remains a separate explicit approval gate.
